# CLAUDE.md — гайд по написанию статей для slava.blog

Этот файл — инструкция для Claude (и людей) о том, **как писать и оформлять
заметки**, чтобы они правильно индексировались поисковиками (Google, Bing,
Яндекс) и попадали в ответы LLM (ChatGPT, Claude, Perplexity, Яндекс Нейро).

Сайт собран на **Quartz 4** (статический генератор). Контент — Markdown-файлы
в `content/`. Домен: `slava.blog`. Локаль по умолчанию: `ru-RU`.

---

## TL;DR чек-лист новой статьи

Перед публикацией каждая заметка должна иметь:

- [ ] Заполненный **frontmatter**: `title`, `description`, `created`, `tags`, `draft: false`
- [ ] **НЕТ строки `# Заголовок`** в теле — заголовок берётся из `title` (правило одного h1)
- [ ] Тело начинается с текста или с `##` (второй уровень и ниже)
- [ ] Осмысленное `description` (120–160 символов) — оно идёт в сниппет поиска и соцкарточку
- [ ] Минимум 2–3 **внутренние ссылки** на другие заметки (`[[wikilink]]`)
- [ ] Если статья важна для EN-аудитории — продублировать смысл или добавить EN-абзац (см. «Двуязычность»)

## 1. Frontmatter (обязательная YAML-шапка)

Каждый `.md` начинается с блока между `---`. Поля, которые реально влияют на
индексацию и отображение:

```yaml
---
created: 2026-06-09T12:00:00+03:00      # дата создания (ISO 8601). См. раздел «Даты»
modified: 2026-06-09T12:00:00+03:00     # дата последнего изменения
title: "Понятный заголовок (English keyword)"   # ОБЯЗАТЕЛЬНО
description: "Одно ёмкое предложение, что внутри и зачем читать."  # ОБЯЗАТЕЛЬНО
tags:
  - product-management
  - knowledge
draft: false                            # true = НЕ публикуется (фильтр RemoveDrafts)
aliases:
  - /старый-или-короткий-url            # опционально: редиректы на эту страницу
---
```

### Что куда идёт (почему поля важны)

| Поле | Куда попадает | Зачем для SEO/LLM |
|---|---|---|
| `title` | `<title>`, `og:title`, `<h1>`, JSON-LD `headline` | Главный сигнал темы. Должен содержать ключевые слова. |
| `description` | `<meta name="description">`, `og:description`, текст соцкартинки, JSON-LD `description` | Сниппет в выдаче. Пиши для человека, 120–160 символов. |
| `created` / `modified` | JSON-LD `datePublished` / `dateModified`, сортировка | Свежесть — фактор ранжирования. Указывай реальные даты. |
| `tags` | граф связей, страницы тегов, навигация | Тематическая кластеризация, дополнительные индексируемые страницы. |
| `draft` | фильтр публикации | `draft: true` полностью исключает страницу из сборки и sitemap. |
| `aliases` | редиректы | Сохраняет ссылочный вес при смене URL. |

### Опциональные поля

- `socialDescription: "..."` — переопределяет текст соцкарточки (если нужен другой, чем `description`).
- `socialImage: "имя-файла.png"` — кастомная OG-картинка из `quartz/static/` (иначе генерится автоматически).
- `lang: "en"` — пометить язык страницы (по умолчанию `ru-RU`). Используй для англоязычных заметок.
- `permalink: "/custom-url"` — задать произвольный URL.
- `enableToc: false` — отключить оглавление на странице.

## 2. Правило одного `<h1>` (критично для SEO)

Компонент `ArticleTitle` **уже выводит `title` из frontmatter как `<h1>`**.

❌ **НЕ делай так** — это создаёт второй h1, Bing/Google ругаются «more than one h1»:
```markdown
---
title: "Моя статья"
---

# Моя статья          ← ДУБЛЬ! Удали эту строку.

Текст...
```

✅ **Делай так** — тело начинается сразу с текста или с `##`:
```markdown
---
title: "Моя статья"
---

Вводный абзац...

## Первая секция     ← заголовки внутри начинаются с h2
### Подсекция        ← дальше h3, h4...
```

**Иерархия заголовков:** `title` = h1 (автоматически) → секции `##` → подсекции
`###` → и т.д. Не пропускай уровни и не используй `#` в теле.

## 3. Заголовок и описание — как писать под поиск

**Title:**
- Конкретный и описательный, отражает суть. Плохо: «Заметки». Хорошо: «Как считать unit-экономику AI-продукта».
- По возможности добавляй **английский ключ в скобках** для двуязычного охвата:
  `"Шпаргалка по продакт-менеджменту (Product Management Cheatsheet)"`.
- Уникальный в пределах сайта (одинаковые title мешают индексации).

**Description:**
- 1 предложение, 120–160 символов, по-человечески (его читают в выдаче).
- Включи 1–2 ключевых термина естественно, без переспама.
- Отвечает на вопрос «что я узнаю и зачем читать».

## 4. Внутренние ссылки и граф

Quartz строит **граф связей и backlinks** между заметками. Чем больше
осмысленных внутренних ссылок — тем лучше краулеры понимают структуру и
важность страниц.

- Ссылайся на другие заметки через wikilink: `[[имя-файла]]` или `[[имя-файла|текст ссылки]]`.
- Новая заметка не должна быть «сиротой» — добавь на неё ссылку хотя бы из одного
  хаба (напр. `pm-study.md` или соответствующего `index.md` раздела).
- Внешние ссылки на авторитетные источники — нормально и полезно.

---

## 5. Даты

- Для **новых** файлов сборка берёт дату из git (последний коммит) как fallback,
  но **надёжнее указать `created`/`modified` явно** в frontmatter в формате ISO 8601
  (`2026-06-09T12:00:00+03:00`).
- При существенном обновлении статьи — **обнови `modified`**. Это сигнал свежести
  для поисковиков (`dateModified` в JSON-LD).
- Не ставь будущие даты.

## 6. Двуязычность (RU + EN)

Цель сайта — находиться и в русском, и в англоязычном пространстве. Сейчас контент
преимущественно на русском — это главный gap по EN.

Рекомендации:
- В `title` добавляй английский ключ в скобках (см. выше) — дёшево и расширяет охват.
- Для статей с потенциалом в EN-аудитории — либо отдельная страница с `lang: "en"`
  и `permalink: /en/...`, либо хотя бы английское резюме (TL;DR) в начале.
- Термины давай в обоих языках при первом упоминании: «оценка спроса (demand
  validation)».

## 7. Структурированные данные и llms.txt (контекст, менять обычно не нужно)

Эти механизмы работают автоматически, но полезно понимать:

- **JSON-LD** (`quartz/components/Head.tsx`): на каждой статье генерится узел
  `BlogPosting` (headline/description/даты/автор) + глобальные `Person` и `WebSite`.
  Person связан с Wikidata `Q140140251` и профилями через `sameAs`. Качество `title`
  и `description` напрямую влияет на этот разметку.
- **llms.txt** (`quartz/plugins/emitters/seoFiles.ts`): краткая выжимка о сайте для
  LLM. Если добавляешь **крупный новый раздел** — впиши его в список разделов в этом
  файле (функция `buildLlmsTxt`).
- **robots.txt** (там же): уже разрешает все поисковые и LLM-боты. Трогать не нужно.
- **sitemap.xml** / **RSS**: генерируются автоматически из контента (плагин
  `ContentIndex`). Новая опубликованная заметка попадает туда сама.

## 8. Файлы, расположение, URL

- Имя файла → часть URL. Используй **короткие латинские slug'и** через дефис:
  `unit-economics-ai.md` → `/unit-economics-ai`. Избегай пробелов и кириллицы в именах.
- Раскладывай по разделам: `content/knowledge/...`, `content/agentic-engineering/...`.
- Раздел-хаб — это `index.md` внутри папки.
- Картинки клади в `content/assets/` и ссылайся относительно.

---

## 9. Чего НЕ делать

- ❌ Не дублировать `title` строкой `# ...` в теле (ломает правило одного h1).
- ❌ Не оставлять пустой/шаблонный `description`.
- ❌ Не публиковать «осиротевшие» страницы без единой входящей ссылки.
- ❌ Не ставить `draft: true` на готовую статью (она не попадёт в индекс).
- ❌ Не использовать `#` (h1) для секций внутри текста — только `##` и ниже.
- ❌ Не дублировать `title` другой страницы — заголовки должны быть уникальны.

## 10. Локальная проверка перед публикацией

```bash
npx quartz build            # собрать сайт в public/
npx quartz build --serve    # собрать и поднять локально для просмотра
```

После сборки можно убедиться, что у страницы ровно один h1:
```bash
grep -oE '<h1[^>]*>' public/<твоя-страница>.html | wc -l   # должно быть 1
```

Публикация: коммит в ветку **`v4`** → GitHub Actions (`.github/workflows/deploy.yml`)
автоматически собирает и деплоит на GitHub Pages. Любой push в `v4` = новый деплой.
